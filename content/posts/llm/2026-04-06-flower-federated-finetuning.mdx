## Flower로 Federated LLM Fine-tuning을 돌리며 겪은 문제와 해결 기록

LLM fine-tuning은 일반적으로 하나의 서버에 데이터를 모아 학습하는 **Centralized Learning** 환경을 기준으로 설명되는 경우가 많다.

하지만 실제 의료, 금융, 기업 내부 데이터처럼 민감한 데이터는 여러 기관이나 사용자에게 분산되어 있고, 모든 데이터를 하나의 서버로 모으기 어려운 경우가 많다. 이런 환경에서는 데이터를 이동시키는 대신 각 client에서 모델을 학습하고 parameter update만 모으는 **Federated Learning(FL)**을 적용할 수 있다.

이번 실험에서는 **Flower 기반 Federated Learning 환경에서 Qwen 계열 LLM을 LoRA fine-tuning**하면서 Medical / Finance 데이터를 이용한 실험을 진행했다.

그런데 실제로 실험을 구성해보니 단순히 기존 LLM fine-tuning 코드를 client 여러 개에서 실행하는 것만으로는 충분하지 않았다.

특히 다음과 같은 문제들이 반복적으로 발생했다.

* GPU OOM
* client 학습 timeout
* Flower round와 local training 간 synchronization 문제
* W&B logging step 초기화
* PEFT adapter 저장 문제
* Qwen architecture와 라이브러리 호환성 문제
* tokenizer / SFTTrainer label masking 문제
* Qwen thinking output으로 인한 benchmark parsing 문제
* client별 데이터 중복 및 비교 실험의 공정성 문제
* 실험 결과 파일 overwrite
* 부가 기능의 예외가 전체 Flower simulation을 종료시키는 문제

이 글에서는 Federated LLM fine-tuning 환경을 구성하면서 실제로 겪었던 문제들과 해결 방법을 정리한다.

---

## 1. 실험 환경

실험은 Flower를 이용해 여러 client가 각각 LLM을 fine-tuning한 뒤 서버에서 update를 aggregation하는 구조로 구성했다.

대략적인 구조는 다음과 같다.

```
text
                    Global Model
                         │
                         ▼
                  Flower Server
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
     Client 0         Client 1         Client N
        │                │                │
   Local SFT         Local SFT         Local SFT
        │                │                │
        └────────────────┼────────────────┘
                         │
                         ▼
                      FedAvg
                         │
                         ▼
               Updated Global Model
```


주요 설정은 다음과 같았다.

| 항목                    | 설정               |
| --------------------- | ---------------- |
| Model                 | Qwen 계열 LLM      |
| Fine-tuning           | LoRA             |
| Quantization          | 4-bit            |
| LoRA rank             | 32               |
| LoRA alpha            | 64               |
| Client 수              | 최대 4 clients     |
| Batch size            | 1                |
| Gradient accumulation | 8                |
| Effective batch size  | 8                |
| Aggregation           | FedAvg           |
| Logging               | Weights & Biases |
| Framework             | Flower           |

Mixed 환경에서는 client domain을 명확하게 고정했다.

```text
Client 0 → Medical
Client 1 → Medical
Client 2 → Finance
Client 3 → Finance
```

이 단순한 구조를 실제로 안정적으로 실행하기까지 생각보다 많은 문제가 발생했다.

---

# 2. 문제 1 — LLM 학습 중 GPU OOM

가장 먼저 만난 문제는 예상대로 **GPU Out Of Memory(OOM)**였다.

LLM은 parameter 자체가 크기 때문에 일반적인 fine-tuning 설정을 그대로 사용하면 client 하나만 실행하더라도 GPU memory를 상당히 많이 사용한다.

Federated Learning에서는 여러 client를 다뤄야 하기 때문에 이 문제가 더 크게 나타난다.

## 해결 방법 1: Batch Size + Gradient Accumulation

실험에서는 실제 batch size를 다음과 같이 낮췄다.

```text
batch_size = 1
gradient_accumulation_steps = 8
```

이를 통해 한 번에 GPU에 올라가는 sample 수는 1개로 줄이면서도 **effective batch size는 8 수준으로 유지**했다.

```text
Effective Batch Size
= batch_size × gradient_accumulation_steps

= 1 × 8
= 8
```

메모리 사용량은 크게 줄일 수 있었지만 단점도 분명했다.

**학습 시간이 길어진다.**

그리고 FL 환경에서는 학습 시간이 길어지는 것이 단순히 실험 시간이 증가하는 문제로 끝나지 않는다.

뒤에서 설명할 **Flower timeout 문제**와 직접 연결된다.

---

## 해결 방법 2: Client를 GPU 하나에서 순차 실행

Flower의 client resource를 다음처럼 설정하는 방법도 사용했다.

```text
client_resources.num_gpus = 1.0
```

하나의 client가 GPU 하나를 전부 사용하는 것으로 설정하면 여러 client가 동시에 GPU memory를 점유하는 문제를 줄일 수 있다.

결과적으로

```text
Memory 사용량 ↓
동시 실행 Client 수 ↓
전체 학습 시간 ↑
```

라는 trade-off가 발생한다.

Federated LLM에서는 단순히 GPU memory만 보는 것이 아니라 **memory와 client concurrency, 전체 round 수행시간을 함께 고려해야 한다.**

# 3. 문제 2 — Client가 아직 학습 중인데 Flower Timeout 발생

OOM을 피하기 위해 batch size를 줄이고 client를 순차 실행시키자 새로운 문제가 발생했다.

**client 한 번의 local training 시간이 너무 길어졌다.**

그런데 Flower server에는 client response를 기다리는 timeout이 존재한다.

실험에서는 client 학습이 아직 끝나지 않았는데 timeout이 발생하면서 정상적인 round 수행이 깨지는 문제가 발생했다.

```text
Server
  │
  ├─ Client 0 training ...
  ├─ Client 1 training ...
  │
  └─ timeout 발생
          ↓
      round 진행 실패
```

LLM fine-tuning은 일반적인 작은 ML 모델보다 local training 시간이 훨씬 길 수 있기 때문에 기본 timeout을 그대로 사용하는 것이 적절하지 않을 수 있었다.

## 해결

Flower의 `server_app.py`에서 사용하는 timeout 설정을 실제 LLM 학습 시간에 맞게 충분히 늘렸다.

여기서 중요한 점은 다음과 같다.

> Federated LLM에서 timeout은 단순한 네트워크 설정이 아니라 하나의 **학습 시스템 parameter**에 가깝다.

local epoch, 데이터 크기, GPU 성능, gradient accumulation 등에 따라 client 한 번의 수행 시간이 크게 달라지기 때문이다.

---

# 4. 문제 3 — W&B에서 Round마다 Step이 다시 시작됨

Federated Learning의 logging에서도 중앙집중식 학습과 다른 문제가 있었다.

각 round에서 client가 새롭게 local training을 실행하다 보니 W&B에는 다음처럼 기록될 수 있었다.

```text
Round 1
Client 0 : step 0 ~ 1500

Round 2
Client 0 : step 0 ~ 1500

Round 3
Client 0 : step 0 ~ 1500
```

이렇게 되면 같은 client가 전체 FL 학습 과정에서 어떻게 변하고 있는지 하나의 연속된 그래프로 확인하기 어렵다.

우리가 실제로 보고 싶은 것은 다음과 같은 형태다.

```text
Round 1 : step    0 ~ 1500
Round 2 : step 1501 ~ 3000
Round 3 : step 3001 ~ 4500
Round 4 : step 4501 ~ 6000
```

## 해결

별도의 **continuous step**을 관리하여 logging하도록 변경했다.

즉,

```text
local_step
```

과

```text
global_continuous_step
```

을 분리했다.

이를 통해 각 client의 loss 변화를 round 경계와 관계없이 연속적으로 확인할 수 있었다.

Federated Learning 실험에서는 단순히 loss를 기록하는 것보다

```text
Client
Round
Local Step
Continuous Step
```

을 함께 관리하는 것이 훨씬 중요했다.

---

# 5. 문제 4 — W&B Timeout

실험 도중 W&B 연결이 지연되면서 timeout이 발생하는 경우도 있었다.

가장 간단한 우회 방법은

```text
wandb.mode = "offline"
```

으로 학습하는 것이다.

이 경우 외부 W&B 서버 연결 상태와 무관하게 학습을 진행할 수 있다.

하지만 이것은 근본적인 해결이라기보다는 **실험 중단을 방지하기 위한 우회 방법**에 가깝다.

특히 장시간 수행되는 Federated LLM 실험에서는 모니터링 시스템의 장애가 실제 학습까지 종료시키지 않도록 구성하는 것이 중요하다.

Logging은 학습을 관찰하기 위한 기능이지, **logging 실패 때문에 학습 자체가 실패해서는 안 된다.**

---

# 6. 문제 5 — Checkpoint를 너무 자주 저장하면 학습이 느려짐

초기에는 학습 상태를 자세히 추적하기 위해 checkpoint를 매우 촘촘하게 저장했다.

예를 들어 100 step마다 checkpoint를 저장하도록 설정했다.

하지만 LLM adapter와 optimizer state 등을 반복해서 저장하면 I/O overhead가 발생한다.

특히 FL에서는 이 과정이

```text
Client × Round × Checkpoint
```

만큼 반복된다.

따라서 checkpoint를 지나치게 촘촘하게 저장하면 전체 학습 시간이 상당히 증가할 수 있다.

실험을 진행하면서 가장 실용적이라고 판단한 방식은

> **각 round에서 각 client의 local training이 끝나는 시점을 중심으로 checkpoint를 저장하는 것**

이었다.

중간 checkpoint가 필요한 실험에서는 간격을 좁힐 수 있지만, 항상 저장 횟수와 전체 학습시간의 trade-off를 고려해야 한다.

---

# 7. 문제 6 — 학습은 끝났는데 PEFT Adapter가 없음

LoRA fine-tuning을 수행했다면 최종적으로 재사용 가능한 **PEFT adapter**가 남아야 한다.

그런데 초기 실험에서는 학습 checkpoint만 존재하고 최종 PEFT adapter가 정상적으로 생성되지 않는 경우가 있었다.

이 상태에서는 loss가 정상적으로 감소했다고 하더라도 해당 실험을 완전히 성공했다고 보기 어려웠다.

따라서 실험 종료 조건에 다음을 포함시켰다.

```text
Training Finished
      ↓
Final Client Update
      ↓
Aggregation
      ↓
Final PEFT Adapter 저장 확인
      ↓
Evaluation
```

또 하나 확인해야 했던 부분은

> 저장된 adapter가 **마지막 학습 시점의 모델인지**, 아니면 **가장 낮은 loss를 기록한 모델인지**

였다.

이 부분은 Trainer의 checkpoint / best model / save 설정에 따라 달라질 수 있기 때문에 코드 수준에서 확인할 필요가 있었다.

결국 단순히

```text
"Flower run이 정상 종료됐다"
```

가 아니라

```text
"재평가 가능한 최종 adapter가 정상 생성됐다"
```

까지 확인해야 하나의 실험이 종료된 것으로 보는 것이 안전했다.

# 8. 문제 7 — Flower 환경의 Transformers가 Qwen Architecture를 인식하지 못함

Qwen3.5 계열 모델을 적용하면서 라이브러리 compatibility 문제도 발생했다.

기존 Flower 예제 환경에서 사용하던 Transformers 버전에서는 새로운 Qwen architecture를 정상적으로 인식하지 못했다.

LLM 학습은 단순히 `transformers` 하나만 맞춘다고 해결되지 않는다.

실제로는 다음 패키지들이 서로 연결되어 있다.

```text
Transformers
    │
    ├── TRL
    ├── PEFT
    ├── Accelerate
    └── BitsAndBytes
```

따라서 모델 architecture를 지원하는 Transformers 버전을 기준으로 **TRL, PEFT 등 관련 라이브러리 호환성을 함께 맞춰야 했다.**

Federated Learning framework가 정상적으로 실행된다고 해서 내부 LLM stack까지 정상적으로 동작한다는 보장은 없었다.

# 9. 문제 8 — SFTTrainer와 Tokenizer Label Masking 문제

SFTTrainer를 이용한 학습 과정에서는 tokenizer와 prompt/completion 처리 방식 때문에 label masking이 예상과 다르게 동작하는 문제도 발생했다.

Instruction tuning에서는 일반적으로

```text
Prompt
Completion
```

전체 sequence 중 실제 loss를 계산할 영역을 결정해야 한다.

우리가 원하는 것은 보통

```text
Prompt      → Loss 계산 X
Completion  → Loss 계산 O
```

이다.

하지만 SFTTrainer의 자동 prompt/completion masking 과정과 tokenizer가 맞지 않으면서 문제가 발생했다.

## 해결

자동 처리에만 의존하지 않고 **prompt 영역의 label을 직접 masking하는 방식으로 변경**했다.

이를 통해 실제 answer에 해당하는 completion 부분에서만 loss가 계산되도록 명확하게 통제했다.

이 문제는 특히 여러 종류의 instruction dataset을 섞어서 사용하는 FL 환경에서 중요했다.

dataset마다 prompt format이 다르면 단순히 dataset을 합치는 것만으로도 예상하지 못한 학습 차이가 발생할 수 있기 때문이다.

---

# 10. 문제 9 — Qwen Thinking Mode 때문에 Benchmark가 깨짐

학습은 정상적으로 끝났는데 benchmark 성능이 이상하게 나오는 경우도 있었다.

원인 중 하나는 Qwen 계열 instruct 모델의 **thinking output**이었다.

Multiple-choice benchmark에서는 보통 다음과 같은 짧은 답을 기대한다.

```text
A
```

또는

```text
yes
no
maybe
```

하지만 모델이 thinking mode를 사용하면 실제 출력은 훨씬 길어질 수 있다.

```text
<think>
...
...
</think>

B
```

이 경우 모델이 정답을 알고 있더라도 evaluator가 답을 정상적으로 parsing하지 못하면 오답으로 처리된다.

실제로 PubMedQA처럼 `yes / no / maybe` 형식을 요구하는 benchmark에서 모델이 `A / B / C` 형식으로 응답하면서 정확도가 크게 떨어지는 현상도 확인했다.

## 대응

평가에서는 다음 부분을 명확하게 통제할 필요가 있었다.

```text
enable_thinking = False
```

또는

```text
max_new_tokens 제한
```

그리고 thinking output이 존재하는 경우

```text
</think>
```

이후의 final answer만 parsing하도록 처리했다.

이 경험을 통해 중요한 사실을 확인할 수 있었다.

> **LLM benchmark에서 낮은 accuracy가 반드시 모델 성능 저하를 의미하지는 않는다.**

출력 format과 evaluator parsing 문제를 먼저 확인해야 한다.

# 11. 문제 10 — Centralized 모델들이 전부 같은 점수를 기록함

Centralized fine-tuning 모델을 평가하던 과정에서는 Medical / Finance / Mixed 모델이 서로 다르게 학습되었음에도 일부 결과가 동일하게 기록되는 이상 현상이 발생했다.

처음에는 학습 자체에 문제가 있다고 생각했다.

하지만 checkpoint와 training log를 확인한 결과 학습은 정상적으로 수행되고 있었다.

결국 원인은 **benchmark evaluation code**에서 발견됐다.

평가 코드를 수정하고 모델들을 다시 평가해야 했다.

이 문제 역시 LLM 실험에서 자주 놓치기 쉬운 부분이다.

```text
Training Bug
```

와

```text
Evaluation Bug
```

를 구분해야 한다.

성능이 이상하다고 바로 fine-tuning 설정을 변경하기 전에 다음 순서로 확인하는 것이 좋았다.

```text
1. Training loss 확인
2. Checkpoint / Adapter 확인
3. 직접 inference 출력 확인
4. Evaluation prompt 확인
5. Answer parser 확인
6. Metric 계산 확인
```

# 12. 문제 11 — Random Split만으로는 Central vs FL 비교가 공정하지 않음

Federated Learning 실험에서는 데이터 분할 방법도 중요한 변수였다.

초기에는 seed를 고정하고 dataset index를 random shuffle하여 client 데이터를 만들었다.

하지만 실험을 반복하면서 dataset을 매번 다시 split하도록 두면 Centralized Learning과 Federated Learning이 실제로 동일한 데이터를 학습했는지 관리하기 어려워진다.

따라서 client별 데이터를 미리 만들어 고정했다.

```text
medical_client0_20k.jsonl
medical_client1_20k.jsonl

finance_client0_20k.jsonl
finance_client1_20k.jsonl
```

방법은 다음과 같다.

```text
전체 index 생성
      ↓
Seed 고정
      ↓
Index shuffle
      ↓
앞 20K → Client 0
다음 20K → Client 1
      ↓
JSONL로 저장
```

이렇게 하면 이후 모든 실험에서 **동일한 client dataset을 그대로 재사용**할 수 있다.

특히 Centralized Learning과 Federated Learning을 비교할 때

```text
학습 데이터
총 데이터 노출량
Epoch
Optimizer
LoRA 설정
```

등을 가능한 한 동일하게 통제할 수 있었다.

결국 seed를 고정하는 것보다 더 확실한 방법은

> **실험에 사용할 subset 자체를 artifact로 만들어 고정하는 것**

이었다.

# 13. 문제 12 — Mixed 실험에서는 Client-Domain Mapping을 반드시 고정해야 함

Medical과 Finance 데이터를 동시에 사용하는 Mixed FL 실험에서는 client와 domain의 mapping 또한 중요한 변수였다.

따라서 다음과 같이 고정했다.

```text
Client 0 = Medical
Client 1 = Medical
Client 2 = Finance
Client 3 = Finance
```

실험마다 client가 다른 domain을 받게 되면 aggregation 결과 차이가

```text
알고리즘 때문인지
데이터 구성 때문인지
client assignment 때문인지
```

구분하기 어려워진다.

FL에서는 centralized training보다 관리해야 할 실험 변수가 많기 때문에 **client identity 자체도 하나의 실험 변수**로 관리해야 했다.

# 14. 문제 13 — Run Name을 다르게 주지 않으면 평가 결과가 덮어써짐

Vanilla / Medical / Finance / Mixed 모델을 같은 evaluation pipeline에서 평가하다 보니 아주 단순하지만 치명적인 문제도 발생했다.

`run-name`을 동일하게 사용하면 기존 결과 파일이 새로운 평가 결과로 덮어써질 수 있었다.

fed_finance_general
fed_finance_finance
fed_finance_medical

fed_mixed_general
fed_mixed_finance
fed_mixed_medical

LLM 실험은 하나의 모델에 여러 benchmark를 실행하는 경우가 많아

```text
Learning Type
Domain
Model
Benchmark
Seed
Round
```

중 필요한 정보를 run name에 포함시키는 것이 안전하다.

# 15. 문제 14 — 알림 코드 하나 때문에 Flower 전체가 Exit Code 700으로 종료됨

실험 시작과 종료를 확인하기 위해 별도의 알림 함수를 붙여 사용하고 있었다.

그런데 외부 API 요청이 정상적으로 수행되지 않은 상황에서 `response` 변수가 생성되지 않았음에도 다음 코드가 실행됐다.

```python
print("Status Code:", response.status_code)
```

결과적으로 다음 오류가 발생했다.

```text
UnboundLocalError:
cannot access local variable 'response'
where it is not associated with a value
```

문제는 단순 알림 기능의 오류였지만, 해당 exception이 `ServerApp`까지 전달되면서 Flower simulation 전체가 종료됐다는 것이다.

최종적으로는 다음과 같은 형태로 나타났다.

```text
RuntimeError: Exception in ServerApp thread
Exit Code: 700
```

즉,

```text
알림 API 실패
    ↓
알림 함수 Exception
    ↓
ServerApp Exception
    ↓
Flower Simulation 종료
```

가 된 것이다.

이 경험 이후 학습과 직접적인 관계가 없는 부가 기능은 반드시 학습 pipeline과 분리하거나 exception을 내부에서 처리해야 한다고 판단했다.

```text
Logging 실패 ≠ Training 실패
Notification 실패 ≠ Training 실패
```

가 되어야 한다.

# 16. 본 실험 전에 Smoke Test를 먼저 수행하기

LLM 학습은 한 번 실행하면 몇 시간 이상 걸릴 수 있다.

그 상태에서 1시간 뒤 tokenizer 오류가 발생하거나 첫 번째 round가 끝난 뒤 Flower 설정 오류가 발견되면 GPU 시간을 그대로 낭비하게 된다.

그래서 본 실험 전에는 아주 작은 설정으로 **smoke test**를 수행했다.

예를 들어

```text
max_steps = 3
max_rows_per_client = 64
```

정도로 실행한다.

Smoke test에서 확인해야 하는 것은 성능이 아니다.

```text
Dataset Loading
      ↓
Tokenization
      ↓
Trainer 생성
      ↓
Forward / Backward
      ↓
Client Update 반환
      ↓
Server Aggregation
      ↓
Checkpoint 저장
      ↓
다음 Round 진행
      ↓
Final PEFT 저장
```

이 전체 pipeline이 정상적으로 한 번 도는지만 확인하면 된다.

Federated LLM에서는 이것만으로도 수 시간의 시행착오를 줄일 수 있었다.

# 17. `flwr run .`만 실행해서 끝이 아니었다

Flower experiment를 실행할 때도 처음에는 단순히 다음 명령을 기준으로 생각했다.

```bash
flwr run .
```

하지만 실제 사용 환경에서는 run 제출 이후 로그를 지속적으로 확인하는 과정이 중요했다.

따라서 별도의 Flower profile을 구성하고 다음 형태로 실행했다.

```bash
flwr run . jj-llm-exp --stream
```

`jj-llm-exp` profile은 별도의 `toml` 설정에 구성했다.

LLM 학습은 수행 시간이 길기 때문에 실행 여부뿐만 아니라

```text
현재 어느 client인가?
현재 어느 round인가?
몇 step까지 진행됐는가?
aggregation은 성공했는가?
```

를 실시간으로 확인할 수 있는 것이 중요했다.

# 18. 결국 Federated LLM Fine-tuning에서 어려웠던 것은 무엇이었나?

실험을 시작할 때는 Federated LLM fine-tuning을 다음 정도로 생각하기 쉽다.

```text
LLM Fine-tuning
+
Flower
+
FedAvg
```

하지만 실제로는 훨씬 많은 요소가 연결되어 있었다.

```text
                        Federated LLM
                              │
            ┌─────────────────┼─────────────────┐
            │                 │                 │
          Model              FL               System
            │                 │                 │
       Tokenizer          Client Split          GPU
       SFTTrainer         Local Steps          Memory
       LoRA / PEFT         Rounds              Timeout
       Quantization       Aggregation          Storage
       Generation         FedAvg               Logging
            │                 │                 │
            └─────────────────┼─────────────────┘
                              │
                          Evaluation
                              │
                      Prompt / Parsing
```

Centralized fine-tuning에서는 주로

```text
loss
learning rate
batch size
epoch
```

에 집중했다면,

Federated Learning에서는 여기에

```text
client별 데이터
client별 학습량
round
aggregation
timeout
client resource
checkpoint
continuous logging
```

까지 관리해야 했다.

# 19. 실험하면서 정리한 체크리스트

이후 Federated LLM fine-tuning 실험에서는 최소한 다음 항목을 확인하고 시작하는 것이 좋았다.

### 데이터

* [ ] Client별 dataset이 고정되어 있는가?
* [ ] Client 간 데이터가 의도치 않게 겹치지 않는가?
* [ ] Central과 FL이 실제로 동일한 데이터를 사용하는가?
* [ ] Mixed 환경의 client-domain mapping이 고정되어 있는가?
* [ ] 총 학습 데이터 노출량이 비교 가능한가?

### LLM

* [ ] Transformers가 해당 model architecture를 지원하는가?
* [ ] TRL / PEFT / Transformers 버전이 호환되는가?
* [ ] Prompt와 Completion의 label masking이 정상적인가?
* [ ] LoRA adapter가 정상적으로 생성되는가?
* [ ] Quantization 설정이 정상적인가?

### Flower

* [ ] Client가 정상적으로 update를 반환하는가?
* [ ] 모든 client가 aggregation에 참여하는가?
* [ ] Local training timeout이 충분한가?
* [ ] 다음 round가 정상적으로 이어지는가?
* [ ] Client별 학습 데이터 위치가 의도대로 이어지는가?

### Resource

* [ ] OOM이 발생하지 않는가?
* [ ] Batch size / Gradient accumulation이 적절한가?
* [ ] 동시에 실행되는 client 수가 GPU 환경에 적절한가?
* [ ] Checkpoint 저장 주기가 지나치게 짧지 않은가?

### Logging

* [ ] W&B 실패가 학습을 종료시키지 않는가?
* [ ] Client와 Round 정보가 함께 저장되는가?
* [ ] Continuous step이 관리되는가?
* [ ] 각 experiment의 run name이 고유한가?

### Evaluation

* [ ] 모델의 실제 생성 결과를 먼저 확인했는가?
* [ ] Thinking mode가 평가에 영향을 주지 않는가?
* [ ] Benchmark가 요구하는 출력 format과 일치하는가?
* [ ] Answer parser가 정상적으로 동작하는가?
* [ ] Evaluation 결과 파일이 서로 덮어써지지 않는가?

### 본 실험 직전

* [ ] `max_steps=3` 수준의 smoke test를 통과했는가?
* [ ] 한 번의 FL round가 처음부터 끝까지 정상 동작하는가?
* [ ] 마지막에 평가 가능한 PEFT adapter가 생성되는가?

# 마무리

Federated LLM fine-tuning을 직접 구성하면서 가장 크게 느낀 점은 **학습 알고리즘만 제대로 구현한다고 실험이 끝나는 것이 아니라는 것**이었다.

특히 LLM처럼 하나의 local training 자체가 많은 GPU memory와 시간을 요구하는 모델에서는

```text
학습량
GPU Memory
Client Scheduling
Communication Round
Timeout
Checkpoint
Logging
```

이 서로 강하게 연결된다.

예를 들어 OOM을 해결하기 위해 batch size를 줄이면 학습 시간이 늘어나고, 학습 시간이 늘어나면 Flower timeout에 걸릴 수 있다.

```text
OOM
 ↓
Batch Size 감소
 ↓
Gradient Accumulation 증가
 ↓
Local Training 시간 증가
 ↓
Flower Timeout 문제
```

즉 각각의 문제를 독립적으로 해결하기보다는 **전체 Federated Learning 시스템 관점에서 자원과 학습 흐름을 함께 관찰해야 한다.**

또한 성능 비교에서도 단순히 Centralized Learning과 Federated Learning의 epoch를 동일하게 두는 것만으로 충분하지 않았다.

client별 데이터 노출량, local step, round, 실제 처리 token 수 등 무엇을 기준으로 학습량을 정합화할 것인지가 중요했다.

결국 Federated LLM 실험에서 필요한 것은 단순한 `loss monitoring`을 넘어,

> **각 client가 어느 round에서 얼마나 많은 데이터와 token을 학습했고, 얼마의 GPU memory와 시간·연산 자원을 사용했는지를 함께 추적할 수 있는 monitoring 구조**

라고 볼 수 있다.

이번 시행착오를 통해 Federated LLM fine-tuning에서는 모델 성능뿐만 아니라 **학습량과 computing resource를 어떻게 측정하고 정합화할 것인가** 역시 중요한 연구 문제라는 것을 확인할 수 있었다.
